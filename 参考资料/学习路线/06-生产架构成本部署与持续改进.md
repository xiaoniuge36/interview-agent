# 生产架构、成本、部署与持续改进

生产化不是把 Notebook 包成 API。它要求模型的不确定决策与身份、事务、队列、版本、预算和观测形成清晰边界，同时为流量和依赖故障准备降级路径。

## 学习目标

- 设计 Product API、Agent Runtime、Worker、Provider 和数据层的职责边界。
- 理解同步请求、流式事件和异步任务的不同一致性要求。
- 用模型路由、缓存、上下文预算和批处理控制单位成功任务成本。
- 建立版本、灰度、回滚、SLO 和数据飞轮。

## 推荐的生产边界

```text
Web / Client
    ↓ identity + intent
Product API ── transaction ── Business Database
    ↓ command / event
Agent Runtime ── state/checkpoint ── Queue / Worker
    ├─ Retrieval Service ── Index
    ├─ Tool Gateway ── Internal/External Systems
    └─ Model Gateway ── Providers
              ↓
       Trace / Metrics / Eval Store
```

Product API 是业务事实与权限入口；Runtime 负责编排；Model Gateway 处理 Provider 差异、路由和用量；Worker 执行长任务。早期可以模块化单体部署，但逻辑边界仍要明确，避免过早微服务化。

## 同步、流式与异步

- 同步：短、确定、需要立即事务结果的操作。
- SSE 流式：单向输出模型 token、阶段状态和进度；断线后按 event ID 续传或重新查询状态。
- WebSocket：确实需要双向实时控制时使用，否则会增加连接治理成本。
- 异步任务：索引、长评测、报告生成和批处理，通过 Queue 解耦并允许重试。

流式文本不等于业务成功。最终状态必须由服务端显式提交；客户端收到一半答案后断线，不能把“连接结束”误判成任务完成。

## 状态、一致性与恢复

为 Command 提供 `requestId`，为运行提供 `runId`，为外部副作用提供 idempotency key。业务事务与队列之间可使用 Outbox；消费者通过去重和状态前置条件实现至少一次投递下的正确行为。

Checkpoint 保存可恢复状态，不保存不可验证的全部模型思维。Prompt、工具、模型、索引和 Schema 都带版本，确保历史运行可解释。

## 成本工程

每成功任务成本比“每次模型调用单价”更重要。常用杠杆：

1. 按任务复杂度做模型路由，低风险步骤使用小模型。
2. 只向模型暴露当前阶段需要的工具和证据。
3. 对稳定前缀、Embedding 和确定性工具结果做安全缓存。
4. 合并可批处理的离线任务，限制并行与最大输出。
5. 用早停、澄清和规则路径避免无意义的 Agent 循环。
6. 记录缓存命中后的真实成本，不把失败重试隐藏掉。

语义缓存必须纳入用户、权限、时效和 Prompt 版本；不能只凭文本相似就跨租户复用答案。模型路由要以评测证明质量底线，而不是只追求价格。

## 容量与降级

容量规划至少观察到达率、服务时间、并发、队列深度和依赖配额。保护顺序通常是：入口限流 → 并发隔离 → 队列背压 → Provider 熔断 → 降级模型/功能 → 明确拒绝。

降级应预先设计，例如关闭非必要 Reflection、降低检索候选数、转为异步报告、返回带来源的检索摘要，或把高风险动作交给人工。不要在故障时临时让模型“自由发挥”。

## 版本、发布与回滚

一次 Agent 发布可能同时改变代码、Prompt、工具 Schema、模型和索引。每项独立版本化，评测结果必须关联完整版本组合。

发布流程：离线回归 → Shadow → 小流量 Canary → 指标对比 → 扩量。回滚不仅回代码，还要考虑 Prompt、索引、Memory 写入格式和未完成任务的兼容性。

## SLO 与持续改进

为用户可感知结果定义 SLO，例如“95% 的合格请求在 20 秒内得到可引用答案”，而不是只监控 API 200。配套错误预算决定何时停止功能迭代、优先修可靠性。

```text
生产 Trace / 用户反馈
          ↓ 脱敏、去重、失败分类
       Bad Case 候选
          ↓ 人工复核与标注
       Golden Dataset
          ↓ 离线实验与消融
       灰度发布与监控
```

数据飞轮不能直接把生产内容自动变成 Prompt 或长期记忆。必须经过授权、脱敏、质量复核和离线评测，避免把攻击样本和错误反馈放大。

## Production Readiness Review

- 身份、租户、权限和审计是否覆盖每个 Tool 与 Retrieval？
- 任务是否有步骤、时间、token、费用和并发预算？
- Provider 故障时是否有限重试、熔断和降级？
- 长任务能否取消、恢复、去重和人工接管？
- Prompt、模型、工具、索引和 Schema 是否可追踪、可回滚？
- 是否存在覆盖质量、安全、延迟和成本的发布门禁？
- 日志是否脱敏，数据是否有保留与删除策略？

## 本课动手实验

把前一课的评测系统部署为一个小型服务：

1. Product API 创建 run，Worker 异步执行，SSE 返回阶段事件。
2. 使用 Fake Provider 做 10、50、100 并发压测，记录队列和 P95。
3. 注入 429 和高延迟，验证退避、熔断、降级与错误预算。
4. 比较两档模型路由和 Prompt 缓存的质量与每成功任务成本。
5. 更换 Prompt 版本做 Canary，满足门禁后扩量，随后演练回滚。
6. 写一份一页 Production Readiness Review，列出仍未解决的风险。

## 自测

1. 为什么流式响应结束不代表业务事务成功？
2. At-least-once Queue 怎样避免重复副作用？
3. 语义缓存为什么必须带权限和版本维度？
4. Prompt 变更为什么也需要灰度和回滚？

## 面试怎么讲

按“边界—数据流—故障—容量—成本—发布”讲系统设计。每一层给出一个指标和一个降级策略，再说明模块化单体到拆分服务的触发条件，能够同时体现 YAGNI 与生产判断。
