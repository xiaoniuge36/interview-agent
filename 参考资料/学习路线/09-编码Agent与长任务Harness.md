# 编码 Agent 与长任务 Harness 工程

Harness 是包裹模型的系统层：上下文组装、工具、权限、子代理、生命周期钩子。生产 Agent 不是 `用户 → Prompt → 模型 → 工具 → 答案`，而是模型作为推理组件嵌在这个系统层里。Terminal-Bench 排行榜上，同一个模型换不同 harness 成绩能相差 20 个百分点以上——脚手架质量经常比换模型更值得投入。

## 学习目标

- 把 harness 拆成可独立演进的正交组件，而不是一坨提示词。
- 掌握子代理作为“上下文防火墙”的用法与回传契约。
- 区分跨会话记忆与会话内压缩这两个常被混淆的问题。
- 会用文件化上下文（AGENTS.md）把项目约定变成可版本化的基础设施。
- 用 pass@1 和 token 成本双指标评估 harness 改动。

## Harness 的正交组件

以 Terminal-Bench 2 上自动演化 harness 的 AHE 研究为参照，一个 harness 可拆成七类互不耦合的组件：系统提示、工具描述、工具实现、中间件、技能（skill）、子代理配置、长期记忆。加一个中间件不需要动系统提示，加一个技能不需要碰任何工具。

该研究还有一个对面试很有价值的消融结论：工具、中间件、长期记忆各自单独迁移都能带来增益，而只迁移系统提示反而回退——结构化的 harness 组件跨任务跨模型可迁移，散文式的策略文字不可迁移。十轮自动演化把 pass@1 从 69.7% 提到 77.0%，超过人工设计的基线。

## 子代理：上下文防火墙

长会话的最大敌人是上下文污染：探索期的海量文件内容淹没后续推理。子代理模式把离散子任务（调研、测试、审查）派发到全新上下文窗口，只回传结构化摘要：

```text
主代理（规划与集成，上下文保持干净）
 ├─ 调研子代理 → {"rootCause": "...", "evidence": [...]}
 ├─ 实现子代理 → {"changedFiles": [...], "testsAdded": 3}
 └─ 审查子代理 → {"blocking": [], "suggestions": [...]}
```

关键契约：子代理拿到的是自包含任务书（它看不到主对话），交回的是 schema 化结果而不是聊天记录。何时值得拆：子任务会产生大量中间内容、可并行、或需要不同权限边界时。

## 记忆与压缩是两个问题

- 记忆回答“什么应该跨会话留存”：项目约定、架构决策、踩过的坑，落到文件或数据库。
- 压缩回答“本会话超长后留什么”：分层递进压缩，近期消息保留原文，久远内容压成决策与结论，而不是简单截断或重启。

把该进长期记忆的内容压缩掉，是长任务 Agent 最常见的慢性失败。判断标准：下个会话还需要的就提升为记忆，只有本会话需要的才交给压缩。

## 文件化上下文：AGENTS.md 当代码管

主流编码 Agent 都收敛到文件化持久上下文：Codex 按目录层级合并 `AGENTS.md`（就近覆盖），Claude Code 用 `CLAUDE.md` 加自动记忆。共同点是外置、随仓库走、可审计。工程要求：

- 当代码对待：进版本库、走评审、可回滚，改动后用固定任务集 A/B 验证。
- 分层作用域：monorepo 里每个子系统一份，避免单个巨型文件全是无关内容。
- 写约束与协议，不写百科：构建命令、测试规范、危险操作清单的价值远高于框架介绍。

检索侧的同类演化：预建索引管线正在被即时检索取代——给 Agent 轻量搜索工具，按需把具体文件拉进工作记忆，而不是预先塞满上下文。

## 脚手架的苦涩教训

暴露宽动作空间和廉价反馈的简单抽象，比精巧的手工控制逻辑活得久。上一代模型必需的复杂多代理辩论和僵硬规划链，对前沿模型反而有害——它们在简单工具加最少干预下表现最好。实践排序（先做前排，后排是挣来的复杂度）：

1. 探索 → 计划 → 执行的显式阶段划分：最小架构换最大可靠性。
2. 渐进式工具暴露：工具超过约 20 个后按阶段解锁，别一次全给。
3. 确定性生命周期钩子：格式化、测试、安全检查放在钩子里强制执行，不依赖模型自觉。
4. 分层记忆与压缩：换取长会话的可控成本。
5. 权限与风险分级：真正的安全边界。
6. 之后才是子代理编排、fork-join、记忆固化。

## 评估 harness 而不是感觉

- Terminal-Bench 2.x：89 个容器化终端任务，自动验证，长程操作能力的事实标准。
- SWE-bench-verified / SWE-bench Pro：真实仓库 issue 修复，衡量仓库级推理。
- 双指标：pass@1 之外必须看 tokens/trial——两个 harness 同分时，成本可以差数倍。
- 改 harness 等于改系统：固定任务集回归，禁止只跑一次凭感觉合并。

## 本课动手实验

为一个真实小仓库搭建最小编码 Agent harness：

1. 写一份分层 `AGENTS.md`：根目录放构建/测试命令与禁改清单，子目录放局部约定。
2. 实现探索 → 计划 → 执行三阶段循环，计划输出为结构化 JSON 并存档。
3. 加两个生命周期钩子：编辑后自动跑 lint，提交前自动跑测试，失败结果回灌模型。
4. 实现一个调研子代理：输入任务书，输出根因摘要 JSON，主代理上下文不增长超过 1KB。
5. 选 10 个固定任务跑基线，改一处 harness（比如压缩策略）后重跑，报告 pass 率与 token 变化。

加分：故意把 `AGENTS.md` 里的测试命令写错，观察钩子失败信息能否让 Agent 自行发现并绕过。

## 自测

1. 为什么“只迁移系统提示会回退，迁移工具和中间件却有增益”？
2. 子代理回传聊天记录而不是结构化摘要，会引发什么问题？
3. 一段“上个会话确定的架构决策”应该进记忆还是进压缩？为什么？
4. 你如何证明一次 harness 改动是提升而不是噪声？

## 面试怎么讲

先抛量化事实：同模型不同 harness 在 Terminal-Bench 上差 20 个百分点，说明系统层是独立于模型的工程杠杆。再讲自己的分层：文件化约定、阶段化循环、确定性钩子、子代理隔离、固定任务集回归。最后用一次 A/B 数据（pass 率与 token 成本同时汇报）证明你是在做工程而不是调咒语。
